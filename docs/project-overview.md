## 项目背景

用户过去做过 Web3 空投、任务、抽奖、社交活动和多账号矩阵，曾通过这类副业获得过较可观收益。过去的工作流主要是在 Windows 上使用多个 Chrome 快捷方式，每个快捷方式指向不同配置文件夹，从而实现多账号环境。

现在用户主要使用 macOS，希望先做一个简单可用的桌面 MVP，解决“多账号 Chrome profile 管理”的基础问题。产品方向参考 AdsPower，但第一版不做 AdsPower 那么重。

## 当前产品定位

MultiChrome 是一个 macOS 优先的多 Chrome 账号档案桌面管理器。

产品审美和交互方向：整体要偏生产力工具，参考 AdsPower 的专业感，但不要照搬它的表格型、臃肿型布局。用户明确不喜欢 AdsPower 那种大表格管理台，更偏好“长方形卡片/小方块启动器”作为主界面承载账号和项目。后续 UI 优化应保持高密度、克制、清晰，但避免把大量低频字段塞回主界面。

第一版只解决一个核心需求：

- 创建多个账号档案。
- 每个账号档案对应一个独立 Chrome `--user-data-dir`。
- 可以给账号写名称、标签、备注。
- 可以批量新建账号，粘贴多行“名称、标签、备注”或从表格复制的 Tab 分隔内容后一次性生成多个账号档案。
- 可以批量删除选中账号；危险操作会先弹独立确认窗口，可选择只删除记录或连同 profile 文件夹一起删除。
- 可以批量扫描导入已有 Chrome profile 文件夹；扫描只读，导入采用复制导入，失败会回滚本次已复制的新目录，并用 `importSource` 与 `.multichrome.json` 防止重复导入。
- 可以一键打开对应独立 Chrome 环境。
- 可以选中多个账号，批量打开同一个指定网址。
- 可以收藏常用网址，并自动记录最近批量打开的网址，方便每日打卡和重复活动入口。
- 可以在左侧“网址库”用 Notion database 风格表格管理结构化常用网址：名称、URL、标签、备注；新建/编辑用弹窗草稿，保存才写入；可回填批量打开输入框，也可用当前选中账号直接打开。
- 可以创建“项目”，每个项目保存多个入口网址、备注、打开间隔和绑定账号，用于长期重复打开空投、抽奖、活动页或平台打卡入口。
- 可以在账号里记录平台资料：平台名称、登录网址、用户名和备注，并可从当前账号 profile 打开登录网址或复制用户名。
- 账号平台资料支持常用模板：X、Discord、Telegram、Gmail、Galxe、Zealy 可一键填入平台名和登录网址；仍然只保存草稿，点击“保存账号”才落盘。
- 元数据和配置目录可以跟随一个根目录迁移。
- V0.2 曾补齐基础管理闭环：归档、删除、复制、导入、浏览器路径设置和批量目录大小刷新；其中归档/状态入口已在后续简化中从 UI 移除。
- V0.3 已将 UI 从三栏管理台改成启动器布局：主界面只保留账号卡片、搜索和少量动作；编辑和设置进入弹窗。
- V0.4 已加入账号颜色标识、标准/紧凑视图、多选、全选当前和批量追加标签。
- 用户确认 `正常/待检查/归档` 对当前 MVP 过重，账号状态管理入口已从 UI 移除；底层 `status` 字段仅保留旧数据兼容。
- 基础维护能力已开始补齐：设置弹窗里新增目录健康检查，可诊断索引文件、profile 目录和孤儿目录问题，可一键修复低风险创建类问题，也可把孤儿 profile 目录手动登记为账号。
- 设置弹窗已加入轻量备份/恢复：备份和恢复 `profiles.json` 账号索引与设置，不包含 Chrome profile 文件夹。
- 设置弹窗已加入完整 profile 备份/恢复：可备份全部账号或当前选中账号的 Chrome profile 文件夹，恢复前会扫描并显示新增/覆盖数量，确认后才执行。
- 窗口管理 V1 已完成前十三步：运行状态识别、进程级切换、窗口数量检查、首个窗口位置/尺寸读取、首个窗口最小化状态读取、平铺窗口小实验、平铺前窗口预检查、窗口操作权限失败提示、平铺可用区域偏移、平铺数量保护、多窗口账号提示、布局同步 V0 和布局同步最小化保护。后端通过 macOS `ps` 扫描 Chrome 主进程的 `--user-data-dir`，识别哪些账号 profile 正在运行；前端在账号卡片显示“运行中”，并给运行中账号提供“切换到账号”按钮。批量栏可对选中且正在运行的账号执行“检查窗口”，通过原生 macOS Accessibility API 枚举窗口标题、窗口位置、尺寸和 `AXMinimized`，并汇总显示首个窗口的 `宽x高 @ x,y`，最小化时追加“已最小化”；也可手动“平铺窗口”。平铺前会先读取每个运行账号的窗口列表，跳过无可读窗口账号，按实际可平铺账号数量重新计算布局，并从 `screen.availLeft/availTop` 表示的可用区域左上角开始摆放。每个平铺窗口按至少 `320x240` 估算，当前屏幕容不下时会提示减少选择或分批平铺，不会移动窗口。平铺仍只移动每个账号的首个 Chrome 窗口；如果账号有多个窗口，完成提示会说明仅平铺首个窗口。布局同步 V0 会读取主账号首个窗口的位置和大小快照，并应用到其它选中且运行、且有可读窗口的账号首个窗口；主窗口最小化时会中止，目标窗口最小化时会跳过。它不做鼠标、键盘、滚动、标签页或网页状态同步。窗口类操作如果遇到 Accessibility API 或权限相关失败，会提示去 macOS 辅助功能权限里允许 MultiChrome 控制电脑，并保留原始错误。
- 用户进一步确认：App 内颜色不是强需求，真正需要研究的是外部已打开窗口或 Dock 图标如何区分不同账号。
- 外部启动器第一轮技术实验已完成：可以为账号生成独立 `.app` 启动入口，每个入口有独立图标和 Bundle ID，但运行中的 Chrome 窗口仍归属 `/Applications/Google Chrome.app`。
- 外部启动器第二轮技术实验已完成并修正：stay-open helper 已从 shell 包装器改成 AppleScript applet，helper 自身保持运行，并通过 `on reopen` 响应 Dock 点击。
- 用户确认双图标体验不理想，外部图标区分实验暂停，不纳入当前 MVP。

## 第一版明确不做

- 不做群控。
- 不做代理。
- 不做浏览器指纹伪装。
- 不做自动任务。
- 不做钱包或社媒自动操作。
- 不做 Windows 适配。
- 不做 AdsPower 级别的浏览器内核和指纹隔离。
- 不做软件内 AI 助手。
- 不做实时窗口同步或群控；当前只保留手动平铺和手动布局同步。

这些可以作为后续阶段再规划。

## 数据目录设计

默认根目录：

```text
~/MultiChromeProfiles
```

目录结构：

```text
MultiChromeProfiles/
  app-data/
    profiles.json
    backups/
      full-profiles-*/
        manifest.json
        profiles.json
        profiles/
  profiles/
    account-001/
    account-002/
```

说明：

- `app-data/profiles.json` 保存账号、项目和设置元数据，跟随根目录迁移。
- `app-data/backups/` 保存轻量账号索引备份，也保存完整 profile 备份目录。
- `app-data/backups/full-profiles-*/` 保存完整备份，包含筛选后的 `profiles.json`、`manifest.json` 和对应 `profiles/account-xxx/` 文件夹。
- `profiles.json` 里包含 `settings.browserPath`，用于保存当前浏览器路径。旧文档没有 `settings` 时会自动使用 `/Applications/Google Chrome.app`。
- `profiles/<profile-id>/` 是 Chrome 的独立用户数据目录。
- 新建账号点“保存账号”后会创建对应目录；点 X 或取消不会留下账号记录或空目录。
- Chrome 第一次打开该 profile 后，才会在目录中生成 `Default`、`Cookies`、`History`、`Preferences` 等真实浏览器配置文件。
- 没安装 Chrome 时，账号记录和空目录仍可以创建，但不能启动浏览器，也不会生成 Chrome 配置内容。

## 当前账号元数据字段

每个账号档案包含：

- `id`：稳定 ID，例如 `account-001`
- `name`：显示名称
- `tags`：标签数组
- `notes`：备注
- `status`：旧版状态字段，可能为 `active`、`needs_check`、`archived`；当前 UI 不再管理它，仅用于兼容旧数据
- `accountPlatforms`：账号平台资料数组，每条包含平台名称、登录网址、用户名和备注；不保存密码
- `accentColor`：账号颜色标识，可为空；老账号为空时按账号编号显示默认色
- `importSource`：可选导入来源信息，包含 `profileUid`、来源路径、来源文件夹名和导入时间；用于批量导入去重
- `createdAt`：创建时间
- `updatedAt`：更新时间
- `lastOpenedAt`：最后打开时间，可为空

全局设置包含：

- `browserPath`：用于启动 profile 的浏览器 `.app` 路径，默认 `/Applications/Google Chrome.app`
- `favoriteUrls`：手动收藏的常用网址，最多保留 20 个
- `recentUrls`：批量打开成功后自动记录的最近网址，最多保留 10 个
- `urlLibrary`：结构化网址库，每条包含名称、URL、标签、备注、创建时间和更新时间；旧版 `favoriteUrls` 会自动迁移到这里，`favoriteUrls` 作为批量栏快捷入口继续保留并同步

## 当前项目元数据字段

每个项目代表“多个网址入口 + 一批绑定账号 + 一个打开节奏”，用于复用过去空投记录里“复制链接再批量打开”的工作流。它只负责打开页面，不自动点击、不自动完成网页任务。

每个项目包含：

- `id`：稳定 ID，例如 `project-001`
- `name`：项目名称
- `url`：主入口网址，保留用于旧数据兼容和快速显示
- `urls`：项目网址列表，每条包含 `id`、`name`、`url`、`notes`
- `notes`：备注
- `profileIds`：绑定账号 ID 数组
- `intervalSeconds`：批量打开账号之间的间隔，当前限制 1-60 秒
- `createdAt`：创建时间
- `updatedAt`：更新时间
- `lastOpenedAt`：最后打开时间，可为空

## 已踩过的坑和修复

### Chrome 打开成文件夹索引页

最初启动参数传成：

```text
--user-data-dir /Users/.../profiles/account-001
```

Chrome 会把后面的路径当成要打开的本地文件夹页面，导致浏览器显示目录索引。

已修复为：

```text
--user-data-dir=/Users/.../profiles/account-001
```

并追加：

```text
--no-first-run
```

后续用户反馈不希望启动后跳转 `about:blank`。已再次修复：保留 `--user-data-dir=/path` 和 `--no-first-run`，不再传起始网址。

```text
src-tauri/src/lib.rs
```

最初“新建账号”只写入 `profiles.json`，没有创建真实目录。用户未打开 Chrome 前点击“打开文件夹”会失败。

相关代码：

```text
src-tauri/src/profile_store.rs

### 删除按钮无响应

V0.2 桌面测试时发现“只删记录”和“删除文件夹”按钮点击后无反应。根因是删除流程依赖 `window.confirm()`，在当前 Tauri WebView 里没有可靠弹出确认框。

已修复：删除操作改为右侧应用内确认面板。用户先点“只删记录”或“删除文件夹”，再点确认面板里的“确认”。

相关代码：

```

## 当前已知限制

- Dock 里的多个 Chrome 图标目前都一样，因为它们来自同一个 `/Applications/Google Chrome.app`。
- macOS 上多个 Chrome profile 的 Dock 图标区分度不如 Windows 快捷方式。
- 简单使用 `open -n -a Google Chrome --args --user-data-dir=...` 无法改变 Dock 图标，因为所有窗口仍来自同一个 Chrome app bundle。
- 第一轮独立 `.app` 启动器已经证明可以区分启动入口，但它本质上仍调用 `/Applications/Google Chrome.app`，所以不保证能改变运行中 Chrome 窗口的 Dock 图标。
- shell stay-open helper 的身份图标虽然能显示在 Dock，但点击无反应；根因是 shell App 不接收 Dock reopen 事件。
- AppleScript applet 修正后，必须用 `osacompile -s` 生成 stay-open App；少了 `-s` 会启动 Chrome 后立即退出。
- 生成 AppleScript applet 后会改写 `Info.plist` 和图标，因此需要本地 ad-hoc 签名，否则 `codesign --verify` 会报 `invalid Info.plist`。
- AppleScript helper 已证明可以常驻并接收 reopen 事件；但真正点击 Dock 后是否能把对应 Chrome profile 拉到前台，仍可能受系统辅助功能权限影响，需要用户肉眼确认。
- 用户决定暂时放弃 Dock 图标区分：因为即使 helper 图标可常驻，Chrome 原生图标仍会同时出现，体验不够干净。
- 后续如 stay-open helper 体验不够，再评估独立浏览器 bundle。复制多个 Chrome app bundle 不推荐，可能带来体积、更新和签名问题。
- 浏览器路径目前通过输入框手动粘贴，不使用原生文件选择器。
- 浏览器路径设置目前只验证路径是否存在，不区分 Chrome / Chromium / Brave / Edge 的兼容差异。
- 账号平台资料库第一版已实现平台、登录网址、用户名和备注；密码安全存储暂未设计，不会把密码明文写入 `profiles.json`。
- 网址库只做本地结构化常用网址管理；不做 favicon、自动标题抓取、AI 扫描导入、账号绑定规则或网页自动填表。
- 网页自动识别输入框并自动填入账号密码暂不做；这需要浏览器扩展或自动化脚本，复杂度和安全风险都高于当前基础功能。
- 尚未实现代理、指纹隔离、群控和任务系统。
- Playwright 自动截图曾因当前环境浏览器自动化问题未完成桌面截图验收。

- 平铺窗口和布局同步已加入设置后的读回验证：只有重新读取到的首个窗口位置/尺寸接近目标 bounds，才算成功；否则提示“未生效”。

后续可做：

- 验证真实桌面上的平铺体验，处理权限失败、窗口最小化、多显示器和 Dock/菜单栏预留空间等边界。
- 目录大小/容量占用如果确实需要展示，优先做左侧独立统计模块。
- 再往后才考虑刷新、前进后退、滚动、点击和输入同步。

### 更远期方向

如果 MVP 稳定，可以逐步走向 AdsPower 类工具的方向：

- UI 继续贴近生产力工具，但坚持启动器卡片为主，不回到大表格主界面。
- 代理配置。
- 基础隔离策略。
- 账号体检。
- 批量打开、手动布局同步，以及更远期的实时窗口同步。
- 群控。
- 项目/任务管理。
- 空投活动记录。
- 社媒账号、钱包、邮箱、Discord、Telegram 绑定信息管理。
- 软件内 AI 助手：左侧或侧边栏聊天入口，用于把用户粘贴的文本整理成项目、批量创建账号草稿、整理标签/备注、辅助导入项目资料；AI 结果必须先预览确认再写入。
- AI 处理账号密码属于更远期安全功能：需要本地安全存储方案，不能默认明文写入 `profiles.json`，也不能默认把敏感资料发给云端模型。

这些都不是当前 MVP 范围。
